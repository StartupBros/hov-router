On a documentation-level read of 16 projects, with nothing installed or measured, HoV Router is not the best in its class today, and no router in the class can show that it is. On routing correctness it is level with or ahead of the field. It is behind on how it protects the logins it holds and on who can install it. Anthropic's usage policy, effective 12 November 2026, now names services that route requests through consumer subscriptions; whether one owner's own accounts fall under it is not settled by any vendor text found, and that is the operator's call. Four ideas survived out of 20 candidates and 5 combinations: close the port by default, encrypt account tokens at rest, cap spend on metered fallback, and a sealed export of accounts. The first pass looked only inside the routing engine and kept nothing. This pass compared the whole product with the field.

Grounding Context

Codebase Context

HoV Router is a self-hosted load balancer for one operator's own provider accounts, with a dashboard for usage, cost and errors. Production is one Linux x86_64 binary behind a guard process, SQLite only. The setup path is a prompt the operator pastes to a coding agent. The product was read at commit 9508061e.

How it compares

Sixteen projects were read on 2026-11-14: nine account poolers and seven multi-provider routers. "Source" means the project's code was read. "Docs" means only its own documentation was read, which is a vendor claim. Our column comes from one read of the code; the facts marked ✓ and every file-and-line citation in this pass were read a second time.

Provider terms

The first pass said the 12 November policy date "is not a basis". It is now. Anthropic's Usage Policy shows "Nov 12, 2026" and bars providing access to Claude through unauthorized means, including "services that route requests through consumer subscriptions or misrepresent the product or client being used". The page was fetched twice today by separate agents. "Unauthorized" is not defined, and one agent reports the bullet is absent from a March 2026 archive copy. The multiple-accounts bullet is limited by purpose: "to avoid detection", to get around guardrails, or to repeat violating inputs.

The Claude Code legal page says OAuth "is designed to support ordinary use of Claude Code and other native Anthropic applications", that developers may not route requests through plan credentials "on behalf of their users", and that they "may not collect, store, or intermediate Claude.ai credentials or session tokens". The Consumer Terms bar automated access except through an API key (one fetch). OpenAI's Help Center describes a permitted path for a ChatGPT plan in "supported open-source tools" (one fetch), and a user's question about a single-operator multi-account proxy, openai/codex #41664, has no OpenAI answer.

Read plainly, the Anthropic sentence describes what any subscription router does. No vendor text found says whether one owner routing their own Claude Code traffic across their own subscriptions is "unauthorized", and no vendor statement of a ban for that case was found. Two first-hand suspension reports exist and are unverified. This page does not settle the question. It affects how much to invest in subscription-specific features, and it is the operator's call.

Limits of this survey

  • Competitor capabilities are mostly documentation claims. Code was read for codex-lb's balancer, OmniRoute's strategy and classifier files, CLIProxyAPI's selector, 9router's fallback and compression, and a few others.
  • General LLM gateways (LiteLLM, Portkey and similar) were read at README level in the first pass only. claude-swap (4,705 stars), claude-relay-service (12,809) and sub2api (46,018) were found and not read.
  • No competitor was installed or run. No measurement was taken on this router.
  • Five items in our own inventory are undetermined: combo hot reload, the default of model-scoped capacity routing, whether route profiles are re-read, Chat Completions inbound, and 402/403 handling.

Topic Axes

  1. Capacity at the edge: what happens to a request when the pool is thin, a limit is ambiguous, or the process restarts.
  2. Credential and exposure safety: how account tokens, the listening port, re-login and recovery are protected.
  3. Operator visibility: what the operator learns without opening the dashboard, and what can be exported.
  4. Client and protocol reach: which clients and request shapes work, and what the router does to the request.
  5. Who can run it, and on what terms: install reach, onboarding, client keys, and how the product scopes itself against provider terms.

The first pass used five routing-internal axes (account choice, stickiness and failover, the record, client contract, who can run it). Its 16 cuts are carried forward in the rejection table under those axes.

Ranked Ideas

  1. S1 · Closed by default
  2. S2 · Account tokens encrypted at rest
  3. S3 · A hard spend cap on metered fallback

Four survivors, fewer than the usual five to seven. Three axes produced none. Each candidate was checked against the code; these four are the ones whose gap was confirmed and which no standing decision rules out. They were candidates N1, N2, N7 and N3, which is why those numbers are missing from the rejection table.

S1

Closed by default

Description
Bind 127.0.0.1 unless the operator widens it. On first start, create an admin key and print it once. Refuse to start on a non-loopback address with no key. Add one exposure line to --doctor: bind address, auth state, TLS, and how many credentials are stored in plain text. Rewrite the top of docs/security.md, which still says "No Authentication" and "No HTTPS" (lines 11 and 14) although keys and TLS flags exist.
Axis
Credential and exposure safety
Basis
direct: apps/server/src/server.ts:2554 reads const hostname = process.env.BETTER_CCFLARE_HOST || "0.0.0.0";. packages/http-api/src/services/auth-service.ts:188 reads "If no API keys are configured, authentication is disabled". docs/security.md:29 has listed "bind to localhost only" as an immediate action since its October 2025 review. external: 9router had about 15 advisories in 2026 including an unauthenticated remote-code-execution flaw, and OmniRoute and CLIProxyAPI had critical or high ones (advisory listings read, not reproduced).
Rationale
A router that is reachable and unauthenticated hands out every login it holds. The documented agent setup already sets the loopback address (docs/agent-setup.md:39) and production binds loopback behind the guard, so the exposed case is anyone who starts the binary another way, and anyone whose agent skips the optional key step (docs/agent-setup.md:53). The audience cannot judge that risk for themselves.
Downsides
It changes a default. Docker must listen on all interfaces inside the container, so the image needs an explicit setting. An existing install reached over a LAN with no key would refuse to start after upgrade until the operator sets one or the other. No incident on this router is cited; the evidence is the competitors' record.

80%

S2

Account tokens encrypted at rest

Description
Encrypt access_token, refresh_token and api_key with AES-256-GCM, using a key the router generates into a root-only file outside the SQLite database. Re-encrypt rows as they are read. --doctor reports how many remain in plain text.
Axis
Credential and exposure safety
Basis
direct: packages/database/src/migrations.ts:574-576 declares api_key TEXT, refresh_token TEXT, access_token TEXT. docs/security.md:30 reads "Plaintext Tokens: OAuth tokens stored unencrypted. Implement AES-256-GCM encryption." The cipher is already in the repo for request payloads (packages/database/src/payload-encryption.ts:4). external: claude-proxy and accountant protect tokens at rest (docs); 9router had advisories for database export exposure and a key leak.
Rationale
The database file is copied more often than the host is broken into: snapshots, .dump files, a support bundle, a backup. Today each copy is a set of live subscription logins. With the key outside the file, a copy is useless on its own.
Downsides
It does not protect against someone with root on the host, who can read the key. The change touches the one table that holds every login, so a migration bug locks the operator out of all accounts at once. An older binary cannot read the ciphertext, which complicates rollback. Lose the key file and every account needs a fresh login. It is also an investment in holding subscription tokens, so its value depends on the open terms question above.
Confidence
70%
Complexity
Medium

S3

A hard spend cap on metered fallback

Description
A dollars-per-day balance for pay-per-use accounts. When the day's metered spend reaches it, the router stops selecting those accounts, returns the normal thin-pool response, and alerts. The operator raises the balance by hand. Spend is counted on accepted successes and on the real upstream model, never on a route alias.
Axis
Capacity at the edge
Basis
reasoned: the only spend control found is an alert. packages/config/src/index.ts:967 defines alert_daily_spend_usd and packages/types/src/alerts.ts:14 lists daily_spend as an alert type; two searches for a cap or budget on accounts and combos found none. An alert tells the operator after the money is spent; an agent in a loop does not wait. external: opencodex gates pay-per-use targets behind consent, claude-proxy has per-user daily dollar limits, prodex has key budgets (all docs).
Rationale
The moment the subscription pool runs dry is the moment an unattended agent spills onto an API key. A fixed ceiling makes that spill safe to leave on, which is the only form of "more capacity at the edge" that does not break a standing decision.
Downsides
No overspend incident on this router is cited; this is reasoned, not observed. It rests on an absence search, and overage and credit-drain handling in packages/proxy/src/handlers/ was not read line by line. It was not determined whether an API-key account in the default pool is already chosen by priority without a combo; if so, a cap changes behaviour for existing installs and needs an "unlimited" default. Cost is an estimate from the price table, and unpriced tokens already show as partial, so the cap can under-count.
Confidence
55%
Complexity
Medium

S4

Sealed export and import of accounts

Description
One command writes accounts, combos, family assignments, client keys and settings into a single passphrase-encrypted file. A second command restores it on a fresh host and lists which accounts still need a login. Build it after S2, on the same envelope.
Axis
Credential and exposure safety
Basis
reasoned: a search of the CLI, docs and scripts for account export, import or backup found only the deploy script's backup of the systemd pin (scripts/deploy-ccflare.sh:603-604). The database file is therefore the only backup, and it is plain text until S2. external: codex-lb imports auth files and TeamClaude syncs tokens between machines (docs); OmniRoute #15190 is an empty database after an update.
Rationale
A lost disk or a move to a new machine costs every login. Repeated re-login is the most-commented complaint in the class.
Downsides
A restore while the original node is still running puts one refresh token in two places. The first to refresh invalidates the other, which is the failure in codex-multi-auth #495. The restore must refuse or warn unless the source is retired. Tokens that rotated since the export need a login anyway, so the saving is partial. This is the weakest of the four. Like S2, it invests in holding subscription tokens, so it depends on the open terms question above.
Confidence
45%
Complexity
Medium

Real but small

These are true gaps that did not earn a card. They are listed so the rejection table does not hide them.

  • Fleet roll-up. "All out at" and "first back at" across accounts do not exist; the per-window data does (packages/http-api/src/handlers/usage-windows.ts:37). A small aggregation.
  • No alert type for an empty pool. Already written as the pool-floor alarm.
  • Stale security doc. docs/security.md:11 and :14 contradict the code. Folded into S1.
  • Chat Completions inbound. The path is recognised in provider code (packages/providers/src/provider-attempt-plan.ts:35), and no inbound translator was found. Unsettled.
