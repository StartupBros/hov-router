Five candidates survived critique, out of 38 raw ideas from five framings. The strongest is the auto-refresh probe code: it is the one inherited feature whose job is to send scripted prompts through subscription accounts. The biggest is the unused provider set. The most consequential decision is whether HoV Router still takes whole upstream releases, because that sets how much every other deletion costs later.

Grounding Context

Codebase Context

HoV Router is a product fork of tombii/better-ccflare (MIT), which derives from snipeship/ccflare. It is a Bun and TypeScript monorepo of about 600k TypeScript lines across apps/cli, apps/server and 21 packages. Only 219 of 708 non-test source files carry no fork commit, so "the fork never touched it" is a weak deletion signal. Production usage is the strong one.

Production is one systemd service, ccflare-stack.service, on SQLite, deployed only from main by scripts/deploy-ccflare.sh. It does not use Docker, npm or PostgreSQL. Read-only queries against the production database on 2026-11-03 showed:

  • Accounts: 14, all with auto-refresh off:
    • anthropic 5
    • codex 3
    • openrouter 2 (paused)
    • openai-compatible 2 (1 paused)
    • xai 1
    • anthropic-compatible 1 (paused)
  • Requests in 30 days: anthropic 480,349; codex 242,394; openai-compatible 20,985; xai 5,578; anthropic-compatible 3. Six of the 18 registered providers have accounts, and five of those six carry traffic.
  • Empty tables: agent_preferences, strategies, request_payloads, oauth_sessions, device_setup_jobs, codex_reset_redemptions, combo_membership_exclusions, and the cache flight recorder tables. The cache flight recorder is a fork feature, so it is out of scope here.
  • Agent attribution, last 7 days: 22,765 requests were attributed by system-prompt agent detection, which feeds anomaly insights. The agents feature is live even though its preference table is empty.

This usage evidence covers the operator's install only. StartupBros and House of Vibe customers install the router too, and their usage is unmeasured.

Constraints every idea respects or flags:

  • Protected operational names stay. AGENTS.md lists the commands, config paths, environment variables, headers, ports, package names and provenance tokens.
  • UPSTREAM.md protects "fork providers and defaults, canonical provider identities" and "SQLite/PostgreSQL migration, repository, retention, and active-window parity".
  • AGENTS.md fences off the upstream publishers and forbids raw scripted Anthropic inference.
  • The generated inline-*-worker.ts files are never touched.

Prior lessons in docs/solutions/ point the same way:

  • Judge inherited code by four checks: call path, production config, client behaviour and kind of harm.
  • The root typecheck skips test files, so a deletion can look green while tests still call the deleted code.

Topic Axes

  1. Inert surface: code nothing in production reaches.
  2. Per-change taxes: inherited code that multiplies the cost of every future change.
  3. Public-distribution machinery: built for upstream's npm, multi-platform and container audience rather than one private deployment.
  4. Active liability: inherited code whose presence alone is a risk.
  5. The upstream relationship itself: the sync protocol and ledgers, plus the compatibility surfaces kept only to make syncs merge cleanly.

Ranked Ideas

  1. Remove auto-refresh's window-opening probes; keep the token refresh
  2. Cut the 11 unused providers and fail loudly on unknown ones
  3. Drop PostgreSQL and make SQLite the only database
  4. Settle the sync policy, then delete the fenced upstream publishers
  5. Remove the per-agent model-preference rewrite; keep detection and the file editor

1. Remove auto-refresh's window-opening probes; keep the token refresh

  • AxisActive liability
  • Confidence85%
  • ComplexityMedium
Description

Delete the code that sends a scripted prompt to an Anthropic, Codex or zai account when its usage window resets, so the next window starts early. That means:

  • the probe method sendDummyMessage;
  • the 500-prompt pool, with its cooldown and backoff;
  • docs/auto-refresh.md;
  • the per-account dashboard toggle.

The same class also hosts two things that are not probes. Keep both:

  • The zai peak-hours pause (checkPeakHoursPause, called at :238). It is a separate opt-in feature, gated on peak_hours_pause_enabled rather than on auto-refresh.
  • OAuth token refresh for Codex and openai-compatible accounts (:340-341).

The token refresh does not run in production today. The scheduler returns at :305-307 when no account has auto_refresh_enabled = 1, and that return comes before the refresh calls. Commit fec5ce18 (2026-07-16) meant the refresh to run on every tick: it removed a later early return but missed this one. Choose explicitly between two options. One is to drop proactive refresh and rely on request-time refresh. The other is to ship the poller as a new, canaried behaviour on the 3 Codex accounts and 1 xAI account. Either way, do not call it a move. Leave the auto_refresh_enabled column in place, unused, so the change needs no migration.

Axis
Active liability
Basis
  • direct: apps/server/src/server.ts:2476-2478 constructs and starts the scheduler on every boot, whatever the account settings.
  • direct: packages/proxy/src/auto-refresh-scheduler.ts:331 calls await this.sendDummyMessage(accountRow). The probe is defined at :391. Token refresh is separate: checkAndRefreshOpenAICompatibleOAuthTokens (:1025) and checkAndRefreshCodexTokens (:1240), both called at :340-341.
  • direct: packages/database/src/migrations.ts:2328 adds auto_refresh_enabled INTEGER DEFAULT 0. Production has it at 0 on all 14 accounts.
  • direct: AGENTS.md: "Raw scripted Anthropic inference remains prohibited".
  • direct: Sizes: the prompt pool is 684 lines, the scheduler 1,887 and the docs 568.
  • external: Anthropic's compliance page, reported by The Register on 2026-02-20, bars using Free, Pro or Max OAuth tokens in other products. There are reports of server-side bans on automated clients. These sources are secondary.
Rationale
This is the one inherited feature whose job is to send scripted prompts through subscription accounts. That is the pattern AGENTS.md forbids and the one most likely to get an account banned. It is off in production, but one dashboard toggle turns it on, and customer installs get the same toggle. Removing it costs no feature anyone here uses, and it shrinks a 1,887-line class whose token refresh is live.
Downsides
  • Keeping the token refresh means switching on background refresh-token rotation that production has never run. Treat it as a new feature, or drop it (above).
  • If a customer turned auto-refresh on, their account would silently lose two things: window-opening, and the auto-resume of failure_threshold and overage pauses (:288-294). Add a startup warning or a release note for rows with the flag set.
  • The auto-refresh endpoint, the autoRefreshEnabled response field and the CLI list field form an external contract. Keep the endpoint as a no-op for one release.
  • About 15 test files drive the class. A few of them cover the rotation-race logic that is kept, so port those before deleting the rest.
  • Cache keepalive also uses the internal-probe auth header, so it stays.
  • The unused column stays until a later schema cleanup, which idea 3 makes cheap.

2. Cut the 11 unused providers and fail loudly on unknown ones

  • AxisInert surface
  • Confidence70%
  • ComplexityHigh
Description

Delete the provider modules no production account uses, in two slices:

  • Slice 1: bedrock, meta, qwen, ollama (with OllamaCloud) and vertex-ai. This is 6,998 of the 7,234 provider-directory lines.
  • Slice 2: zai and the five thin anthropic-compatible wrappers: minimax, deepseek, kilo, nanogpt and alibaba-coding-plan.

Each slice also removes the provider's add-account flow, usage fetcher, type constants and dashboard branches.

Replace the unconditional registration list with an allowlist of the six providers that have accounts: anthropic, codex, openai-compatible, xai, openrouter and anthropic-compatible. Make startup report an error naming any account row whose provider is no longer registered, instead of leaving that account silently unroutable.

Axis
Inert surface
Basis
  • direct: packages/providers/src/index.ts:85-102 registers all 18 providers unconditionally.
  • direct: Provider-directory source lines, measured this run: bedrock 4,551; meta 828; qwen 692; ollama 562; vertex-ai 365; zai 114; nanogpt 30; alibaba-coding-plan 30; kilo 26; minimax 18; deepseek 18. Per the scanner's counts, usage fetchers add about 940 lines and tests about 9k more.
  • direct: Production has no account on any of the 11 and no request to them in 30 days.
  • direct: UPSTREAM.md:21-22 protects "fork providers and defaults, canonical provider identities" in general terms. It names none of the 11.
  • external: LiteLLM keeps first-class providers in its tree and reaches the long tail through a generic OpenAI-compatible route, which is the shape the allowlist leaves here.
Rationale
Each provider name is spread across 13 to 56 files: types, both migration files, the dashboard and the CLI's add-account flows. Every routing or schema change therefore pays for providers nobody here runs. Bedrock alone is 4,551 lines of AWS signing and translation code. The allowlist stops the set from growing back, and it turns a stale account row into a visible error.
Downsides
  • The usage evidence covers only the operator's install. Customers may run ollama or deepseek, so ask them first, especially before slice 2.
  • AGENTS.md names ollama as an example account for scripted testing; change that to litellm or omniroute through openai-compatible. AGENTS.md also has a Qwen provider section, which goes with qwen.
  • The root typecheck skips test files, so caller sweeps (with grep -a; some files contain NUL bytes) and per-file test runs have to carry the proof.
  • An account whose provider is no longer registered is not rejected today. packages/providers/src/registry.ts:90-94 falls back to the request's provider, and so do token-manager.ts:824 and model-catalog.ts:540, so a leftover account could send its credentials through the wrong adapter. The startup check must pause such accounts and the fallbacks must fail closed. A fatal error would be a new way for a customer install to fail to boot.
  • Customers would lose real capabilities with no replacement:
    • Qwen OAuth add and re-auth;
    • Bedrock and Vertex cloud-credential accounts, including the Bedrock cache prewarm;
    • the Ollama translation;
    • the local and cloud-credential combo route classes, whose only producers are ollama, bedrock and vertex-ai.
    An openai-compatible account substitutes only for key-based endpoints. Ship a log-only release first to see whether anyone has these accounts.
  • Leave BUNDLED_PRICING, the historical migrations, the routing-revision trigger lists and the oauth_sessions CHECK untouched. Pruning them risks GLM and DeepSeek pricing and changes the deploy schema digest.

3. Drop PostgreSQL and make SQLite the only database

  • AxisPer-change taxes
  • Confidence60%
  • ComplexityHigh
Description

Delete:

  • packages/database/src/migrations-pg.ts;
  • the PostgreSQL branches in the database package;
  • the PG-only tests;
  • the PG steps and the postgres:16 service container in .github/workflows/managed-routing-postgres.yml.

Keep that workflow's required job id, managed-routing-foundation, and its SQLite steps. Amend the parity clause in UPSTREAM.md and the dual-migration rule in AGENTS.md.

Do this before the other schema deletions. After it, dropping a table or column is one migration instead of five touch points.

Axis
Per-change taxes
Basis
  • direct: migrations-pg.ts is 2,941 lines.
  • direct: AGENTS.md: "Every migration added to packages/database/src/migrations.ts MUST also be ported to packages/database/src/migrations-pg.ts", followed by a five-step checklist for each schema change.
  • direct: UPSTREAM.md:24 protects "SQLite/PostgreSQL migration, repository, retention, and active-window parity". Step 4 of the release-sync protocol requires "SQLite/PG parity and restore rehearsal".
  • direct: managed-routing-postgres.yml runs the SQLite managed-routing tests (lines 58-64) before its PostgreSQL steps. Its job is one of the two required checks on main.
  • direct: Production runs SQLite. Git history shows tombii added PostgreSQL on 2026-03-03 "for Kubernetes deployments".
Rationale
PostgreSQL is the largest standing tax in the tree. It doubles every schema change, adds a live-database service to CI, and adds a parity duty to every upstream sync, and nothing here runs it. Removing it first also makes the other deletions here cheaper: auto-refresh's column, agent_preferences and the dead strategies table each become a single SQLite migration.
Downsides
  • It reverses two written protected contracts, so it is the operator's call.
  • It closes the door on multi-pod hosting until someone rebuilds that.
  • The 397 PostgreSQL references across 69 database files include the adapter both backends share, so the PG-only cut is smaller than that count. It has not been measured.
  • The database package moves further from upstream. That matters only if wholesale syncs continue (idea 4).
  • Deleting migrations-pg.ts alone breaks every production deploy. scripts/deploy-ccflare.sh:473 reads it with readFileSync to build the schema digest, under set -Eeuo pipefail. Drop it from that list in the same PR, and expect one full-stack restart the first time, because a changed digest makes the backend-only handoff ineligible.
  • The release tooling pins the workflow file name managed-routing-postgres.yml and its display name (scripts/router-release.ts:427,438-439). Strip only the services block and the PostgreSQL steps.
  • About 20 test files import migrations-pg, including the kept SQLite test managed-routing-migrations.test.ts. upstream-review-workflow-security.test.ts:84-95 asserts the postgres service. Split these tests rather than deleting them.
  • Without a guard, a machine with a postgres:// DATABASE_URL would silently fall through to an empty SQLite file (database-operations.ts:540-547, :601-603). Fail fast instead, and pin a final PostgreSQL release.
  • Keep BunSqlAdapter: it is the live SQLite adapter, and only its PostgreSQL branches go.

4. Settle the sync policy, then delete the fenced upstream publishers

  • AxisThe upstream relationship itself
  • Confidence55%
  • ComplexityMedium
Description

Decide whether HoV Router still takes whole upstream releases as two-parent merges. The alternative is cherry-picks only, each judged by the fork-network survey's four checks: call path, production config, client behaviour and kind of harm.

If the answer is cherry-picks, delete what exists only to make wholesale merges clean:

  • upstream's release.yml, release-dispatch.yml, signpath-release.yml, signpath-test.yml and .signpath/;
  • the prepublishOnly and postpublish npm hooks, and the macOS, Windows and arm64 build aliases. Keep apps/cli/build-multi-arch.ts, build:multi and build:linux-amd64: the router's own release build runs them (apps/cli/router-artifacts.ts:154-167, reached by the required prepare check);
  • the fence test and AGENTS.md's fence rule.

Archive scripts/verify-upstream-sync-ledger.ts, and record each removed subsystem as one line in UPSTREAM.md. Keep the v3.5.78 ledger, LICENSE, the acknowledgements and the tombii build classification.

Axis
The upstream relationship itself
Basis
  • direct: UPSTREAM.md:5: "Manual, pinned source integration when an upstream release is worth adopting; targeted cherry-picks otherwise". UPSTREAM.md also lays out a five-step release-sync protocol built around "one real two-parent merge commit".
  • direct: scripts/__tests__/router-release-workflow.test.ts:728-771 requires the four upstream publisher workflows to exist, and each job's condition to evaluate to false for this repository.
  • direct: scripts/verify-upstream-sync-ledger.ts is 2,124 lines. The last wholesale sync was v3.5.78 (PR #339, 2026-09).
  • direct: The fork-network survey of 2026-10-31 reviewed 1,539 commits across 146 forks to land 3 PRs (docs/solutions/workflow-issues/survey-the-fork-network-then-check-each-port-applies-here.md).
  • reasoned: Under wholesale merges, every file that ideas 1-3 delete becomes a modify/delete conflict whenever upstream edits it. The fenced publishers stay so that their upstream edits merge cleanly. Under cherry-picks, deletions cost nothing later and the fences protect nothing.
Rationale
This decision sets how hard the rest of the teardown can go. The publisher files are already fenced and tested, so deleting them alone gains little; the rejection table says why. What they cost is upkeep tied to a sync model the fork may no longer need.
Downsides
  • It is a strategic call, not an obvious tear-out.
  • Upstream security fixes would then arrive only through surveys and cherry-picks.
  • It amends the written protocol but does not break it: UPSTREAM.md promises no automatic upstream tracking.
  • tool-drop-announce.yml stays. It is the fork's own Discord announce lane, not upstream code.
  • Upstream provider and proxy fixes would arrive only by survey, among them Codex stream hardening (Codex carries about 240k requests a month). Give the survey a schedule and an owner before ending wholesale syncs.
  • Edit these files in the same PR:
    • tests/bun-toolchain-pin.test.ts:10-18 and auto-rerun-failed.yml:37;
    • build-multi-arch.test.ts:581-601, splitting the test so its provenance cases stay;
    • the fence test.
    Replace the fence with a small test that fails if the four workflow files reappear, because release.yml fires on any v* tag.
  • Archive the sync verifier, its test and the closeout doc at a git tag rather than deleting them. Keep AGENTS.md's no-npm-publish rule when the fence sentence is rewritten.

5. Remove the per-agent model-preference rewrite; keep detection and the file editor

  • AxisInert surface
  • Confidence65%
  • ComplexityLow
Description

Delete the per-agent model preference stored in the database:

  • agent-preference.repository.ts. Leave the agent_preferences table and the migration files alone: dropping the table would destroy any customer's rows and would change the deploy schema digest;
  • the two preference lookups in agent-interceptor.ts;
  • the preference API routes;
  • the dashboard's model-preference selector.

Keep agent detection and attribution, and keep the dashboard's agent-file editor.

Axis
Inert surface
Basis
  • direct: packages/proxy/src/handlers/agent-interceptor.ts:166 and :334 await dbOps.getAgentPreference(...) on requests with a detected agent.
  • direct: The routes are at packages/http-api/src/router.ts:600 (POST /api/agents/bulk-preference) and :996-1010 (per-agent POST and DELETE .../preference). The dashboard control is components/agents/AgentModelPreferenceSelect.tsx.
  • direct: agent_preferences has 0 rows in production.
  • direct: In the last 7 days, agent detection attributed 22,765 production requests (lean-collector 17,492, lean-reader 5,271), and anomaly insights key on that attribution (#367).
  • direct: Commits #705 and #706, on 2026-11-02 and 11-03, fixed the agent-file editor. The editor writes the frontmatter model that Claude Code itself reads.
Rationale
The rewrite is a branch in the request path that can swap a model, and nobody has configured it. Cutting it removes a surprise from the hot path and drops a table, while the parts of the agents feature that production uses stay.
Downsides
  • The win is small. The rewrite guards and the original_model/applied_model columns stay, because the opt-in frontmatter fallback needs them.
  • It removes the only per-agent model override that works without editing the agent's file. Agents declared by header (x-better-ccflare-agent-id, agent-interceptor.ts:161-195) could then be attributed but never rerouted.
  • A customer who already set preferences would silently lose them, because the fallback is off by default. Log a warning when rows exist.
  • GET /api/agents calls getAllAgentPreferences without a guard, and the dashboard selector is imported by the agent editor, so all of these must go in one change.
  • Production behaviour is unchanged: with 0 rows, both lookups already return nothing.
  • The frontmatter-model fallback is a separate switch: leave it until production config confirms it is off.
